# 代码审查技能

对代码改动（diff、PR、或指定文件）做结构化审查。先读相邻代码与既有约定，再逐维度过。

## 规则

- 只报告有依据的问题：每个结论都要能指到具体文件与行；没有读过的代码不下结论。
- 按严重级分级：blocker（必须改：正确性 / 安全 / 数据丢失风险）、should（应该改：可维护性 / 性能）、nit（可选：风格 / 命名）。
- 建议要可执行：说清改成什么、为什么，而不是只指出「不好」。
- 肯定做得对的地方，尤其是容易被误改的防御性代码——但夸奖不超过问题的篇幅。

## 工作流

1. 读改动全貌：`git diff` 或目标文件，列出改动的意图与影响面。
2. 正确性：边界条件、错误路径、并发与状态、协议兼容（上游请求 / 错误映射 / 工具拼装）。
3. 安全：路径穿越、注入（shell / SQL / 模板）、密钥与日志泄露、权限门控是否被绕过。
4. 性能：无界循环、重复计算、同步 IO 热路径、不必要的全量读取。
5. 风格与测试：与周边代码风格一致；新行为是否有测试守着；坏味道（死代码、魔法数、过深嵌套）。
6. 汇总：按严重级列出问题清单，每条带文件与行号、理由、建议改法；没有问题就说「未发现 blocker / should 级问题」。

## 禁止

- 禁止只看改动不看上下文就下结论。
- 禁止把个人偏好包装成 blocker。
- 禁止一次审查里同时改代码——审查只出报告，改动等用户确认。
