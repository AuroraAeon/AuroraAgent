# 文件新鲜度与原子落盘

## 文件新鲜度

模型隔好几轮依据记忆去改文件，期间用户在编辑器里动过同一处——`edit_file` 若按旧内容拼接，会悄悄覆盖用户的改动。文件新鲜度追踪防的就是这个。

- `read_file` 记下文件的 `(mtimeMs, size)` 指纹
- `edit_file` / `write_file` 落笔前比对：不一致即「本次会话里被外部改过」，先把原内容重读一遍（工具本来就要读），再在工具结果里告知模型「以上结果基于刚刚重新读到的内容」
- 自己写完刷新指纹，否则每次 edit 都会把自己上次的写当成外部改动
- 文件被外部删掉也算「改过」：`edit_file` 自己会报不存在，但 `write_file` 会静默把它重建，那正好抹掉用户删文件的意图
- 按回合建档，回合结束清空

**为什么用指纹快照而不是 `fs.watch`**：watcher 要给每个文件养一个，还得区分「自己写的」与「别人改的」（否则每次 edit 都误报），长会话就是一堆 fd 和竞态。APFS 的 mtime 是纳秒级，指纹比对足够可靠且完全确定性——测试不必等文件系统事件。

## 原子落盘

配置、会话、提供方、消息队列、定时任务、故障转移状态等文件统一走 `writeFileAtomic`：写临时文件 → `fsync` → `rename` → 目录 `fsync`。

- 临时文件显式 `chmod 0600`：`open` 的 mode 受 umask 影响，不钉死就可能全局可读——这些文件含 API Key、会话转录与任务全文
- 数据目录按 `0700` 创建
- 半截文件是数据事故、全局可读是泄露事故，两头都堵
